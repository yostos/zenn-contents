## TL;DR

OOPの中核（クラス継承・型階層・参照セマンティクス）を意図的に排除したGo言語の視点から、GoFの23パターンが現代でも有用かを再検討しました。

- GoFの23パターンのうち、**10パターンはOOPの制約への処方箋**であり、Go言語のように制約を排除した言語では不要になった
- **Iteratorは言語機能に吸収**され、**Singletonは設計手法の進化で非推奨**となった
- **残る11パターンは言語やパラダイムに依存しない普遍的な設計原則**であり、現代でも有用である
- GoFの本質的価値は23のカタログそのものではなく、ソフトウェアの複雑さに名前を付けて共有可能な知識として体系化した営みにある

## はじめに

1994年にGoF（Gang of Four）が体系化した23のデザインパターンは、OOP（オブジェクト指向プログラミング）で良いコードを書くための手本として広く受け入れられました。しかし、2009年にGoogleが公開したGo言語は、OOPの中核であるクラス継承・型階層・参照セマンティクスを意図的に排除しています。

もしGoFのパターンがOOPの仕組みに依存したものであるなら、Go言語では成立しないはずです。逆に、パラダイムに依存しない普遍的な設計原則が含まれているなら、形を変えて生き残るはずです。本記事ではこの仮説を検証します。

## Go言語の3つの設計方針

Go言語の設計はOOPとの対比で、次の3点に集約されます。

- クラス継承を排除し、合成（composition）と暗黙的インターフェースで代替
- 参照セマンティクスではなく値セマンティクスをデフォルトに
- 振る舞いをオブジェクトに包む制約を廃し、第一級関数とチャネル/ゴルーチンで直接扱う

この設計方針により、GoFの23パターンは以下の4つに分類されます。

## 1. OOPの制約への処方箋として不要になった10パターン

### クラス継承の副作用への処方箋（4パターン）

**Template Method、Factory Method、Abstract Factory、Bridge**

OOPでは開放閉鎖原則を実現するためにクラス継承が使われましたが、継承自体が脆弱な基底クラス問題や密結合を引き起こしました。これらのパターンは「継承をどう安全に使うか」の処方箋です。Go言語には継承がないため、副作用もなく、処方箋も不要です。

### 参照セマンティクスを補完するパターン（2パターン）

**Prototype、Memento**

OOPの参照セマンティクス[^semantics]の世界では、オブジェクトの正しいコピーや状態の保存・復元が設計上の課題でした。Go言語では値セマンティクスにより、構造体の代入がそのままコピーになります。`saved := currentState`で保存、`currentState = saved`で復元できるため、パターンとしての仕組みは不要です。

[^semantics]: 参照セマンティクス（reference semantics）とは、変数への代入がオブジェクトの参照（ポインタ）をコピーする振る舞いのこと。代入先を変更すると元のオブジェクトも影響を受ける。Java、Pythonなどが採用している。一方、値セマンティクス（value semantics）とは、変数への代入がデータそのものをコピーする振る舞いのこと。代入先を変更しても元のデータには影響しない。Go言語の構造体やC言語の構造体が採用している。

### 振る舞いをオブジェクトに包む制約への処方箋（4パターン）

**Strategy、Command、Visitor、Observer**

OOPの「すべてがオブジェクト」という原則は、関数を1つ渡したいだけでもインターフェース定義、具象クラス実装、インスタンス生成の儀式を強制しました。Go言語では第一級関数とチャネル/ゴルーチンにより、これらの儀式は不要です。

たとえばStrategyパターンは、Javaではインターフェース・具象クラス・コンテキストクラスの3層が必要ですが、Go言語では関数を引数として渡すだけで実現できます。

```go
// ソート順を関数として受け取る。クラスもインターフェースも不要
func executeSort(data []int, less func(i, j int) bool) {
    sort.Slice(data, less)
}

data := []int{3, 1, 4, 1, 5}
executeSort(data, func(i, j int) bool { return data[i] < data[j] })  // 昇順
executeSort(data, func(i, j int) bool { return data[i] > data[j] })  // 降順
```

## 2. 言語機能として吸収された1パターン

**Iterator**

イテレータの有用性が広く認められた結果、現代の言語では標準機能として取り込まれました。Go 1.23で導入された`iter.Seq`を使うと、Javaで4ファイル約80行必要だったカスタムイテレータが、関数1つで実現できます。

```go
type BookShelf struct {
    books []Book
}

func (s *BookShelf) All() iter.Seq[Book] {
    return func(yield func(Book) bool) {
        for _, book := range s.books {
            if !yield(book) {
                return
            }
        }
    }
}

// 使用側：range でそのまま回せる
for book := range shelf.All() {
    fmt.Println(book.Name)
}
```

## 3. 設計手法の進化で非推奨となった1パターン

**Singleton**

OOPの副作用とは無関係に、現代の多くの設計指針で非推奨とされるパターンです。問題の本質は「インスタンスが1つ」ではなく「グローバルなアクセス手段を提供する」点にあります。`GetConfig()`のようなグローバル関数を通じてどこからでもアクセスできることが、隠れた依存関係を生み、テスト時のモック差し替えを困難にします。

現代では依存性の注入（DI）がより優れた解法として確立されています。必要な依存を明示的に引数として渡すことで、グローバル状態を排除し、テスト容易性と可読性を確保できます。

以下は、DB接続設定（Config）をSingletonのグローバル関数ではなく、コンストラクタの引数として`UserRepository`に注入する例です。

```go
type Config struct {
    DBHost string
    DBPort int
}

type UserRepository struct {
    config Config
}

// 依存が引数として明示されている
func NewUserRepository(config Config) *UserRepository {
    return &UserRepository{config: config}
}

func (r *UserRepository) FindByID(id int) (*User, error) {
    dsn := fmt.Sprintf("%s:%d/mydb", r.config.DBHost, r.config.DBPort)
    // ...
}
```

`UserRepository`が何に依存しているかが`NewUserRepository`の引数として明示されており、テスト時には異なる`Config`を渡すだけで済みます。

## 4. 現代でも有用な11パターン

残る11パターンはOOPに依存せず、ソフトウェア設計の普遍的な課題を解決するものです。

| 分類 | パターン |
|------|----------|
| 小さな部品を合成して大きな振る舞いを作る | Composite, Decorator, Chain of Responsibility, Builder |
| コンポーネント間の境界を制御する | Adapter, Facade, Proxy, Mediator |
| 状態に応じて振る舞いを切り替える | State |
| 特定領域の問題を解決する | Flyweight, Interpreter |

これらはGoFの23パターンの中に混在していた「ソフトウェアアーキテクチャの原則」であり、言語やパラダイムを超えて有効です。

## 結論 — デザインパターンの本質的価値

GoFの23パターンには性質の異なる2種類のものが混在していました。

- **実装の工夫** — OOPの未成熟さをカバーする処方箋。パラダイムが変われば不要になる
- **普遍的な設計原則** — 合成による構築、境界の制御など、OOPとは無関係にソフトウェアの複雑さに対処するアーキテクチャの知恵

Go言語が示したのは、OOPの制約に起因するパターンは言語設計で解消できるということです。そして残った11のパターンこそが、GoFの本質的な遺産「言語やパラダイムを超えた設計原則」だったと言えます。

ただし、この結論も永続的ではありません。Rustの列挙型はStateパターンを言語機能として吸収しつつあり、名前付き引数を持つ言語ではBuilderの必要性が薄れます。デザインパターンの本質的な価値は、23のカタログそのものにはなく、ソフトウェアの複雑さに名前を付け、共有可能な知識として体系化しようとした試み — その営みにこそあったのではないでしょうか。
