## TL;DR

- ターミナルのフォントは欧文・和文・アイコンの3段フォールバックで組む
- 送り幅を`fontTools`と`wezterm ls-fonts`で実測し、`scale`と`font_size`を決める
- `scale`は「欧文フォントの送り幅 ÷ 和文フォントの半角送り幅」で求まる
- WezTermはセル幅を整数に丸めるため、成立する`font_size`は限られる
- East Asian Ambiguousの字幅は、端末の数え方（WezTermの既定は1セル）と一致させる
- `font_rules`はフォールバック連鎖を丸ごと置き換えるため、太字と斜体でも3段を組み直す

## なぜマージフォントを使用しないのか

ターミナルに適したフォントとして、[白源](https://github.com/yuru7/HackGen)や[UDEV Gothic](https://github.com/yuru7/udev-gothic)など、コーディングに適した欧文フォントと日本語フォントをマージした素晴らしいフォントは既に存在しています。これらを使えば、1つのフォントをターミナルに設定するだけでフォントの設定は完了します。フォントにあまり拘りがない方は、これらのマージフォントを使用するほうが合理的です。

しかし、これらのフォントは基本的に再配布可能な欧文フォントと日本語フォントの組み合わせしかありません。特定のフォント、例えば「[Fantasque Sans Mono](https://github.com/belluzj/fantasque-sans)が使いたい」としても、誰かがこのフォントを使ったマージフォントを作ってくれるのを待つしかありません。[Berkeley Mono](https://usgraphics.com/products/berkeley-mono)のような有償フォントは、改変や再配布が不可なので原理的にマージフォントを作ることができません。

また、マージフォントでは、収録されているウェイトが限られていたりイタリックが収録されない場合も多くあります。その場合斜体などの表現はターミナルが疑似的に表現することとなります。

どうしても好みのフォントを使用したい場合、マージフォントを使用せずに欧文と和文でフォントを使い分ける必要があります。多くのターミナルではフォントのフォールバック機能[^1]が実装されています。この機能を使えば、欧文と和文フォントを個別に設定できます。

[^1]: 複数のフォントを指定し、文字のグリフが最初のフォントの見つからなかった場合に、次のフォントからグリフを探す機能。

## ターミナルのフォント設定が難しい理由

ターミナルは文字を等幅のマス目に並べて表示します。このマス目をセルと呼びます。欧文1文字がセル1つ、日本語1文字がセル2つにちょうど収まらないと、日本語混じりの表や罫線が崩れます。

欧文の等幅フォントには日本語のグリフが含まれていないものが多く、その場合は日本語を別のフォントへフォールバックさせる必要があります。ところが欧文フォントと和文フォントは、文字幅の基準そのものが違います。何も考えずに並べると、全角文字がセル2つに収まりません。

マージフォントでは作者がこれらの欧文と和文フォントの違いを予め調整してくれていますが、ターミナルのフォールバック機能で文字を合わせる場合はこれらの調整を自身で行なう必要があります。

この記事では、欧文に[Berkeley Mono](https://berkeleygraphics.com/typefaces/berkeley-mono/)、和文に[更紗ゴシック（Sarasa Gothic）](https://github.com/be5invis/Sarasa-Gothic)を使う構成を例に、フォントの組み合わせを実測で決める手順を説明します。フォントの銘柄が違っても、手順そのものはそのまま使えます。

## 3段フォールバックという考え方

役割ごとにフォントを分け、優先順位を付けて並べます。私は次のように欧文、和文に加えて、アイコン文字も別途指定することにしました[^2]。

| 役割     | 担当するフォント           | 例                     |
| -------- | -------------------------- | ---------------------- |
| 欧文     | 好みの等幅フォント         | Berkeley Mono          |
| 和文     | 半角と全角が1対2のフォント | Sarasa Term J          |
| アイコン | シンボル専用のNerd Font    | Symbols Nerd Font Mono |

WezTermは`font_with_fallback`に並べた順序で文字を探します。欧文フォントに無い日本語は和文フォントへ、どちらにも無いアイコンはシンボルフォントへ落ちる仕組みです。

[^2]: マージフォントの多くは、Nerd Fontのパッチが当てられています。

WezTermにはSymbols Nerd Font Monoが同梱されており、何も設定しなくてもフォールバック連鎖の末尾に入ります。筆者がアイコンの解決先を29点サンプリングしたところ、23点は内蔵フォントで解決しました。Powerlineの区切りはWezTerm自身が描画しています。豆腐になったのは`U+E6B5`と`U+EC1E`の2点だけでした。多くの場合は内蔵版で足ります。単体版を入れると、内蔵版の古いビルドで欠けている文字が埋まります。Homebrewが入っていれば、Macでは以下の手順でSymbols Nerd Font Monoを導入できます。

```bash
brew install --cask font-symbols-only-nerd-font
```

## 送り幅を実測する

フォント設定は見た目で判断すると、微妙なズレを見逃します。数値で確認しましょう。測る対象は送り幅です。1文字を描いたあと、次の文字の位置までカーソルが進む距離を指します。

2つのツールを使用します。ひとつは`fontTools`です。フォントファイルそのものを読み、`hmtx`テーブルから送り幅を取り出します。以下は導入予定の欧文と和文フォントについて確認しています。

```python:probe.py
from fontTools.ttLib import TTFont
from pathlib import Path

# ttc は fontNumber でフェイスを選ぶ。220 は Sarasa Term J Regular
FONTS = [
    ("Berkeley Mono Regular", "BerkeleyMono-Regular.otf", 0),
    ("Sarasa Term J Regular", "Sarasa-SuperTTC.ttc", 220),
]
CHARS = [("A", 0x41), ("あ", 0x3042), ("①", 0x2460)]

for label, name, index in FONTS:
    f = TTFont(Path.home() / "Library/Fonts" / name, fontNumber=index, lazy=True)
    upem = f["head"].unitsPerEm
    cmap = f.getBestCmap()
    cols = []
    for char, cp in CHARS:
        gid = cmap.get(cp)
        adv = f"{f['hmtx'][gid][0] / upem:.3f} em" if gid else "-"
        cols.append(f"{char} {adv:>8}")
    print(f"{label:24}" + "  ".join(cols))
```

```text
Berkeley Mono Regular   A 0.600 em  あ        -  ①        -
Sarasa Term J Regular   A 0.500 em  あ 1.000 em  ① 0.500 em
```

emは文字サイズを1とする単位なので、この値はフォントサイズに左右されない設計値です。Berkeley Monoは`A`を0.600 emで送り、日本語のグリフを持ちません。更紗ゴシックは半角が0.500 em、全角が1.000 emで、`①`は半角側に置かれています。2つのフォントは幅の基準そのものが違う、という事実がここで分かります。

次にWezTerm自身の`ls-fonts`です。設定を与えたときに、実際どのファイルのどのフェイスが選ばれ、送り幅がいくつになるかを返します。`--codepoints`には調べたい文字をUnicodeのコードポイントで渡します。`41`はU+0041の`A`、`3042`はU+3042、ひらがなの「あ」です。ここで読み込む`test.lua`は、Berkeley Monoと更紗ゴシックを並べただけの素の設定です。

```bash:check.sh
wezterm --config-file ./test.lua ls-fonts --codepoints 41,3042
```

```text
0 A  \u{41}   x_adv=12 cells=1 wezterm.font("Berkeley Mono", ...)
1 あ \u{3042} x_adv=20 cells=2 wezterm.font("Sarasa Term J", ...)
```

上記の結果から次のことがわかります。

`A`はBerkeley Monoから取られ、送り幅を表す`x_adv`は12ピクセル、占める幅は`cells=1`で1セルです。ここから1セルの幅が12ピクセルだと実測で分かります。「あ」は更紗ゴシックから取られ、`cells=2`は2セルを占めるべき文字だというWezTermの判定です。2セルなら24ピクセル必要なのに、`x_adv`は20ピクセルしかありません。4ピクセル足りない状態です。この4ピクセルをどう埋めるかが次節の話になります。ここがズレたままだと表示が崩れます。

フォントファイルの設計値と、WezTermが実際に採用する値は一致しないことがあります。2つのツールを突き合わせる理由はここにあります。

## scaleで和文の幅を合わせる

先ほどの4ピクセルの不足を、フォントの設計値で見直します。セルの幅は欧文フォントが決めるので、例では0.600 emです。全角が収まるべき2セルは1.200 emになります。一方で更紗ゴシックの全角は1.000 emなので、そのまま並べると0.200 em足りません。

WezTermの`scale`は、フォールバック先のフォントを何倍で描くかを指定するオプションです。求める倍率は次の式になります。

```text
scale = 欧文フォントの送り幅 ÷ 和文フォントの半角送り幅
```

例では`0.600 ÷ 0.500 = 1.2`です。これで和文の半角が欧文のセル幅と一致し、全角はその2倍になります。総当たりで確認した結果が次の表です。

| scale | セル幅 | `あ`（要24） | `①`（要12） |
| ----- | ------ | ------------ | ----------- |
| 1.1   | 12     | 22           | 11          |
| 1.15  | 12     | 23           | 12          |
| 1.2   | 12     | **24**       | **12**      |
| 1.25  | 12     | 25           | 13          |

## font_sizeは自由に選べない

ここで厄介な事情があります。WezTermはセル幅をピクセルの整数に丸めます。「欧文の送り幅 × font_size」が整数から離れると、丸めの誤差でグリッドが崩れます。`font_size`を振って確かめた結果が次の表です。

| font_size | セル幅 | `あ` | `①` | 判定          |
| --------- | ------ | ---- | --- | ------------- |
| 16.0      | 10     | 19   | 10  | 全角が1px不足 |
| 18.0      | 11     | 22   | 11  | ぴったり      |
| 19.0      | 11     | 23   | 12  | 1px超過       |
| 20.0      | 12     | 24   | 12  | ぴったり      |
| 21.0      | 13     | 25   | 13  | 全角が1px不足 |
| 22.0      | 13     | 26   | 13  | ぴったり      |
| 24.0      | 14     | 29   | 15  | 1px超過       |

成立するサイズは限られています。この例では18.0、20.0、22.0が使え、筆者は20.0を選びました。21.0や24.0へ動かすと桁がずれます。

⌘+と⌘−でサイズを変える運用をしていると、崩れる場面に出会います。なぜこの値なのかを忘れた頃に自分を助けるので、実測値ごと設定ファイルへコメントとして残しておくとよいでしょう。

## Ambiguousをどちらに倒すか

和文フォントを選ぶ前に、East Asian Ambiguousの話を挟みます。半角と全角のどちらとも解釈しうる文字のことで、`①②③`や`◆`、`※`あたりが該当します。

AmbiguousはUnicodeのEast Asian Widthプロパティで`A`に分類される文字です。狭幅と広幅のどちらにも解決されうる、という分類までがUnicodeの担当です。どちらに倒すかを決めるのは端末側になります。WezTermには`treat_east_asian_ambiguous_width_as_wide`という設定があり、既定は`false`、つまり1セルとして数えます。したがって「半角が正しい」のではなく、端末の数え方とフォントの字幅が一致していることが要件になります。

端末が1セルと数えている文字に、2セル分の字幅を当てるとどうなるでしょうか。隣へはみ出すだけでは済みません。カーソル位置は1桁しか進みません。そのため以降の再描画で、端末が消したつもりの位置と実際に塗られた位置がずれます。消し残りや行の崩れとして表面化します。

では全角側に倒せばよいかというと、こちらも通りません。Ambiguousに含まれるのは丸数字や記号だけではないからです。罫線の`─│┌`、矢印`→`、`°`と`±`、ギリシャ文字、キリル文字が該当します。Nerd Fontのアイコンやpowerlineの区切りにも、ここに属するものが多くあります。多くはUnicodeの私用領域を使っているためです。私用領域は`E000..F8FF`が丸ごとAmbiguousに分類されます。

`treat_east_asian_ambiguous_width_as_wide = true`を指定すると、これらは一斉に2セル幅へ変わります。プロンプトの区切りとアイコン、`tree`や`gh`の引く枠線まで、横幅が倍になります。`①`を正しく出すためにプロンプトと罫線を組み直すのは割に合わないので、半角側に倒します。コードポイント範囲ごとに幅を指定する`cell_widths`を使えば私用領域だけを全角へ固定できますが、これはnightlyビルド限定の設定です。手元の安定版20240203-110809-5046fc22は受け付けませんでした。

Vimの`ambiwidth=double`に代表される全角前提の設定は、日本語環境では長く標準でした。常時目に入る文字の中身がこれだけ変わった今は、半角側のほうが破綻は少なくなっています。

## 和文フォントの選定基準

日本語フォントなら何でもよいわけではありません。判断の軸は3つあります。

第一の軸は、いま見たAmbiguousの字幅です。端末が1セルと数える以上、和文フォント側も半角で設計されている必要があります。

macOS標準のヒラギノ角ゴシックは、これらを全角で設計しています。手元の構成で測ると、セル幅12に対して送り幅は13.75でした。25パーセントはみ出して隣の文字と干渉します。しかも`scale`を振っても解消しませんでした。

更紗ゴシックはAmbiguousを半角として設計した系統です。`①`と`◆`はどちらも0.500 emで、`scale = 1.2`を掛けるとちょうど1セルに収まります。ただし同じ更紗ゴシックでも"Mono"系統はAmbiguousが全角なので、ターミナルには"Term"系統を選ぶ必要があります。またSCを選ぶと漢字が中国字形になるため、日本語環境では日本語字形を意味する"J"を選びます。

第二の軸は漢字のカバレッジです。ここは数え方に注意が必要でした。

| フォント             | JIS X 0208 | JIS X 0213 | Unicode CJK統合漢字 |
| -------------------- | ---------- | ---------- | ------------------- |
| Sarasa Term J        | 100 %      | 100 %      | 100 %               |
| ヒラギノ角ゴ Sans W3 | 100 %      | 85.3 %     | 51.3 %              |

ヒラギノの51.3パーセントは一見すると低く見えます。しかしUnicodeのCJK統合漢字ブロックは、日本語・簡体字・繁体字・韓国・ベトナムの漢字をすべて含む集合です。日本語フォントの評価軸としては適切ではありません。PythonのShift_JISコーデックで判定したところ、ヒラギノに無い1万225字のうちJIS X 0208に含まれるものは0字でした。常用漢字と人名用漢字は完全にカバーしています。

なおmacOS全体では、標準フォントを合わせるとCJK統合漢字を100パーセント表示できます。ただし日本語フォントに無い字はHiragino Sans GB（簡体字）やHeiti TC（繁体字）へ落ちるため、表示はされても字形が中国字体になります。更紗ゴシックを使うと、この落下自体が起きません。

第三の軸はウェイトとイタリックの実フェイスです。ターミナルは斜体をコメントの表示に使うため、実フェイスの有無は実用差になります。更紗ゴシックはウェイトが5段（200 / 300 / 400 / 600 / 700）あり、それぞれにイタリックを持つので、合計10面すべてが実フェイスです。nameID 1では`Sarasa Term J Light`のように枝番のファミリ名へ分かれますが、nameID 16のタイポグラフィックファミリは10面とも`Sarasa Term J`で共通です。したがってファミリ名は変えず、`weight`を指定するだけで切り替わります。日本語フォントにイタリックがあるのは珍しく、ヒラギノはW0からW9まで10段のウェイトを持ちながらイタリックを1面も持ちません。

## 更紗ゴシックの中身

更紗ゴシックはRenzhi Li（Belleve Invis）氏によるOFL-1.1のフォントです。[Iosevka](https://typeof.net/Iosevka/)の作者でもあります。

フォントファイルの著作権表記を見ると、素性が分かります。

```text
Copyright (c) 2015-2025, Renzhi Li (aka. Belleve Invis, belleve@typeof.net).
Portions Copyright (c) 2016 The Inter Project Authors.
Portions Copyright (c) 2014-2021 Adobe Systems Incorporated.
Portions Copyright (c) 2012 Google Inc.
```

Adobeが源ノ角ゴシック（Source Han Sans）、GoogleがNoto Sans CJKです。つまり更紗ゴシックの漢字とかなは源ノ角ゴシックそのもので、作者の仕事はIosevkaの欧文と合成し、半角と全角を厳密に1対2のグリッドへ再設計することでした。今回の構成では欧文をBerkeley Monoが担当するので、更紗ゴシックは実質的に「ターミナル用に幅を再設計した源ノ角ゴシック」として働いています。

この再設計は、源ノ角ゴシックをそのまま使わない理由でもあります。両者を実測しました。

| 文字         | 源ノ角ゴシック JP | 更紗ゴシック Term J |
| ------------ | ----------------: | ------------------: |
| `①` `◆` `※` |          1.000 em |            0.500 em |
| `─` `→`      |          1.000 em |            0.500 em |
| `°`          |          0.370 em |            0.500 em |
| `α`          |          0.625 em |            0.500 em |
| `あ` `漢`    |          1.000 em |            1.000 em |

源ノ角ゴシックはAmbiguousを全角に置き、`°`や`α`は字ごとの固有幅を持ちます。一般の文書組版としては妥当ですが、さきほど述べたAmbiguousの条件を満たしません。更紗ゴシックのTerm系統は、これらをすべて0.500 emへ揃えています。かなと漢字の字形が同じであっても、ターミナルで使えるかどうかはこの一点により決まります。

供給元についても触れておきます。フォントは実行ファイルではなく、ネットワークアクセスとテレメトリのいずれも持ちません。理論上の懸念はTrueTypeのヒンティング命令ですが、更紗ゴシックのヒンティングはttfautohintによる自動生成です。macOSのCoreTextはフォント解析をサンドボックス下で行います。GitHub Releasesから手動でダウンロードするとチェックサムの検証がないため、筆者はHomebrewのcask経由に切り替えました。

```bash
brew install --cask font-sarasa-gothic
```

ライセンスはOFL-1.1で、撤回できません。一度入手したものを後から使えなくされる事態は原理的に起きないので、単一ベンダーの商用フォントより安心できます。

## font_rulesの落とし穴

設定の該当部分です。`font_rules`は指定したフォントで丸ごと置き換わる仕様なので、太字と斜体でも同じ3段を組み直す必要があります。ここを怠ると、太字の日本語やアイコンがフォールバックから外れます。

```lua:wezterm.lua
local function font_stack(weight, italic)
 return wezterm.font_with_fallback({
  { family = "Berkeley Mono", weight = weight, style = italic and "Oblique" or "Normal" },
  -- Sarasa は Oblique を持たず Italic
  { family = "Sarasa Term J", weight = weight, style = italic and "Italic" or "Normal", scale = 1.2 },
  { family = "Symbols Nerd Font Mono" },
 })
end

config.font = font_stack(400, false)

config.bold_brightens_ansi_colors = true
config.font_rules = {
 { intensity = "Bold", font = font_stack(700, false) },
 { italic = true, font = font_stack(400, true) },
 { italic = true, intensity = "Bold", font = font_stack(700, true) },
}
```

斜体のスタイル名がフォントごとに違う点にも注意が必要です。Berkeley MonoはOblique、更紗ゴシックはItalicを持ちます。上のコードのように、フォントごとに正しい名前を渡します。

## 結果を検証する

設定後に送り幅を検証すると、次のようになります。

```text
A      x_adv=12  cells=1   1セルぴったり
あ 漢  x_adv=24  cells=2   2セルぴったり
① ◆   x_adv=12  cells=1   1セルぴったり
```

日本語混じりの表や罫線が崩れなくなり、`①`のような記号も隣の文字と重ならなくなりました。太字と斜体は、欧文がBerkeley Monoの設計どおりのOblique、和文が更紗ゴシックの実イタリックで描かれます。合成は発生していません。

実際の表示です。日本語と欧文が混ざっても、文字がマス目からはみ出さずに並んでいます。

和文を1.2倍で描いているため日本語が欧文よりやや大きく見えますが、筆者はこちらの方が読みやすく感じています。欧文がまとまって見えるので、コード交じりの文章も読みやすくなりました。

## まとめ

手順をまとめると、次の5ステップになります。

1. 欧文フォントの送り幅を`fontTools`で測る
2. 和文フォントの半角送り幅で割り、`scale`を求める
3. `ls-fonts`で`font_size`を振り、全角が2セルへ収まる値を探す
4. Ambiguousの字幅が端末の数え方と一致する和文フォントを選ぶ
5. `font_rules`で太字と斜体にも同じ3段を組み直す

フォントの銘柄が変わっても、この流れは変わりません。見た目の勘に頼らず数値で決めておくと、あとから設定を触るときにも迷わなくなります。
